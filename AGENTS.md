# audio-scope-view

## Frontend (web app) gotchas
- The home recordings list reads `useRecentRecordings` (query `GET_RECENT_RECORDINGS`), NOT `useRecordings` (`GET_RECORDINGS`). Any recording mutation (pin/rename/delete/create) must refetch `GET_RECENT_RECORDINGS` too, or the home list shows stale pin/rename/delete state. See `RECENT_RECORDINGS_REFETCH` in `apps/vyzorWeb/src/hooks/use-recordings.ts`.
- Main scroll container is `apps/vyzorWeb/src/root.tsx:55` (`overflow-y-auto`), which clips absolutely-positioned dropdowns that extend beyond it. `position: fixed` dialogs (session-settings, create-session) escape this, but their downward dropdowns can still run off the viewport on mobile — `InlineSelect` flips up / clamps `maxHeight` to available space to handle this.
- More-menu / popover z-index: use `z-50` (sticky header is `z-30`). The recordings more-menu previously used `z-10` and rendered behind later rows.
- GraphQL fragments/queries were verified to match the Rust schema via introspection (SESSION_FIELDS, RECORDING_FIELDS, RECORDING_SUMMARY_FIELDS, SessionWithStatusFields, all wrapper result types).

## Docker / Client-Server Connection (IMPORTANT)
- The deployed image bundles a static-server (Node, port 3000) that serves the SPA and reverse-proxies `/graphql` and `/ws` to the Rust backend (127.0.0.1:8080 inside the container). So the browser must use **relative** endpoints (`/graphql`, `/ws`), NOT absolute `ws://localhost:8080/...` URLs — the browser's `localhost` is not the container's localhost, so absolute URLs break in Docker/remote deploys.
- `packages/api-client/src/config.ts` `DEFAULT_CONFIG`: `graphqlEndpoint: "/graphql"`, `websocketEndpoint: "/ws"`. `apps/vyzorWeb/src/hooks/use-waveform-stream.ts` builds the WS URL from `location.host` + `/ws`. `.env.example` and `render.yaml` set `VITE_WEBSOCKET_ENDPOINT=/ws`.
- `VITE_*` env vars are baked into the frontend bundle at **build** time (Vite), not read at runtime. A deployed image with stale/empty build-time env will be broken regardless of runtime env — rebuild the image to pick up new values.
- **Image freshness matters:** the ghcr image must be rebuilt from current source after client-side changes. A stale image renders the UI but the Apollo client may silently fail to fire queries (no POST /graphql in server logs). Always rebuild + redeploy after frontend fixes.
- Run locally: `docker run -p 3000:3000 -p 8080:8080 -e BOOTSTRAP_KEY="$(openssl rand -hex 32)" ghcr.io/vinnsedesigner/audio-scope-view:latest`. Health: `curl http://localhost:3000/health`.
- Dev frontend (no Docker): `pnpm --filter @audio-scope-view/vyzor-web dev` (add a `server.proxy` in vite.config.ts pointing `/graphql`+`/ws` at the backend port to test against a running server).

## Turso HTTP API Integration

### Architecture
- `infrastructure/turso_http_client.rs`: TursoClient uses Turso v2 pipeline API (`POST /v2/pipeline`)
- All repos (`repo_turso_*.rs`) use parameterized queries (`?` placeholders) for SQL injection safety
- `TursoArg` enum serializes bound parameters with `{"type":"text/integer/float/null","value":...}` tags

### Key Gotchas (Fixed)
1. **NaN/Infinity serialization**: serde_json serializes `f32::NEG_INFINITY`/`NaN` as `null`, which Turso rejects for NOT NULL columns. `TursoArg::float()` sanitizes non-finite values to 0.0.
2. **SELECT * column ordering**: `ALTER TABLE ADD COLUMN` appends columns to the end, breaking positional index assumptions in `row_to_*` mappers. Use explicit column lists (e.g. `RECORDING_COLUMNS` constant in recording repo, explicit SELECT in user_preferences repo) instead of `SELECT *`. Affected: recordings (sample_rate added by migration 008), user_preferences (auto_close_timeout_secs).
3. **Multi-statement SQL**: Turso v2 API rejects multi-statement SQL strings. `database_connection.rs` splits them before sending.
4. **TursoResult enum**: Match on `TursoResult::Ok(ok)` to extract results, `TursoResult::Error { error }` for errors.

## Device-ID Scoping (IMPORTANT)
- **No user-facing auth.** Sessions/preferences are scoped to a device via the `X-Device-Id` HTTP header (no sign-up/login). A larger platform will wrap this app as a feature with its own auth later.
- Frontend: `apps/vyzorWeb/src/hooks/use-device-id.ts` (`useDeviceId`) generates/persists a UUID per browser (localStorage). The api-client attaches it as `X-Device-Id` on every request and as a query param on the WS connection.
- Backend: `extract_auth_header` middleware reads `Authorization` + `X-Device-Id` and inserts them as `AuthHeaderExt(Option<String>)` / `DeviceIdExt(Option<String>)` newtype wrappers into the request extensions. **These must be distinct types** — axum's `Extension` map is keyed by type, so two `Option<String>` inserts collide and the second overwrites the first (previously caused the device-id value to clobber the auth-header value, breaking all auth).
- `RequestIdentity` (built in `graphql_handler`) carries `device_id` + `is_system_client` + `api_key`; resolvers read it via `ctx.data::<RequestIdentity>()` and use `device_scope_from_context(ctx)` to scope queries/mutations.
- Ownership checks: batch recording ops (`deleteRecording`, `deleteRecordings`, `pinRecordings`) verify each item belongs to the device. Subscription resolvers (`waveform_subscribe`, `spectrum_subscribe`, etc.) verify session ownership before streaming. `endSession`/`updateSessionDsp` only affect sessions owned by the requesting device.
- **WebSocket auth + scoping:** The WS handshake (`/ws`) is behind the same `extract_auth_header` middleware. Because browsers cannot set custom headers on a WebSocket handshake, the frontend also sends `X-Device-Id` and `X-Api-Key` as query params (`WsHandshakeQuery`), which the `ws_handler` merges with any header values. The handler authenticates the bootstrap/API key (401 on failure), builds a `RequestIdentity`, and passes it + the `SessionService` into `handle_socket`. Every `Subscribe`/`SubscribeSpectrum`/`WaveformData`/`AnalysisData` message is checked by `verify_ws_session_ownership` against `session.user_id == device_id` before acting — so a device cannot subscribe to or publish into another device's session.
- User preferences: `prefs_id` = device id (falls back to `"default"` for system/admin calls with no device id).
- Verified end-to-end: device A's sessions/preferences are invisible to device B; unauthenticated requests are rejected.

## GraphQL Subscriptions over WebSocket (Apollo `graphql-ws` protocol)
- The app exposes TWO WebSocket endpoints — do not confuse them:
  - `/ws` — legacy binary streaming protocol (waveform/spectrum frames, `Subscribe`/`WaveformData` JSON messages). Used by `use-waveform-stream.ts`.
  - `/graphql/ws` — Apollo `graphql-transport-ws` subprotocol for `@apollo/client` subscriptions (`analysisSubscribe`, etc.). Used by `use-scope-capture.ts` via the Apollo `WebSocketLink`.
- Backend (`rust/src/api/server_graphql.rs`): `graphql_ws_handler` serves `/graphql/ws`. The `WebSocketUpgrade` MUST call `.protocols(["graphql-transport-ws"])` so axum echoes the subprotocol back — without it the browser's `WebSocket` never fires `open` (subprotocol negotiation fails). `GraphqlWsHandshakeQuery` reads `X-Device-Id` / `X-Api-Key` from serde-renamed query params and authenticates the same way as `/ws`.
- Frontend (`packages/api-client/src/audioScopeView/graphql/client.ts`): the Apollo `WebSocketLink` connects to `ws(s)://<host>/graphql/ws?X-Device-Id=<deviceId>` (device id appended as a query param because browsers cannot set custom headers on a WS handshake). `@apollo/client/link/ws` depends on `subscriptions-transport-ws` as a peer dep — install it (`pnpm --filter @audio-scope-view/vyzor-web add subscriptions-transport-ws`) or the import resolves to `undefined` and subscriptions silently never connect.
- Static-server proxy (`apps/vyzorWeb/scripts/static-server.cjs`): the WS upgrade handler proxies `/graphql/ws` (and `/ws`) to the backend. CRITICAL: the `http.request`/`http.upgrade` options MUST include `port: 8080` — without it Node defaults the target port to 80 and the upgrade fails silently. Also inject `X-Device-Id` / `Authorization` headers into the proxied WS handshake request when the browser omits them.
- Verification: a working subscription shows `GQL-WS: AUTH OK (device: <id>)` in the backend log and NO `ws close`/`error` lines. Direct test against 8080 and through the 3003 proxy should both reach `connection_ack`.

## Device-scoped data access (security fix)
- The `X-Device-Id` header is the data-isolation dimension. `is_valid_device_id()` in `rust/src/shared/constants.rs` validates canonical UUID form (`8-4-4-4-12` hex) and the legacy `dev-<base36>-<base36>` fallback. Malformed ids are rejected with HTTP 400 at the middleware (`server_graphql.rs::extract_auth_header`) and both WS handshake handlers (`ws_handler`, `graphql_ws_handler`).
- Device scoping is enforced at the **resolver** layer via ownership helpers (`assert_session_ownership`, `assert_settings_session_owned`, `assert_waveform_session_owned`): before reading/mutating a session-scoped resource, verify the session's `user_id` equals the requesting device id. Unscoped admins (bootstrap key, no device id) bypass the check. Denials return "not found" rather than "forbidden" to avoid leaking existence.
- Settings CRUD, Waveform CRUD, `capture`, `updateSessionDsp`, `createSubSession`, `subSessions`, `parentSession`, `exportWaveform`, and `startBatchCapture` all enforce ownership. API key management (`apiKeys`, `apiKey`, `verifyApiKey`, `createApiKey`, `updateApiKey`, `deleteApiKey`) is gated behind `assert_admin` (bootstrap-only).
- `static-server.cjs` explicitly forwards `X-Device-Id` (not just via `...req.headers` spread) in the `/graphql`, `/api/`, and WS upgrade proxy paths.
- `createSession` derives `user_id` from the request device id (ignores client-supplied `input.user_id` for non-admins).

## DSP core: C++ → WASM → TS (architecture migration, Step 3 complete)
- **Single source of truth:** the DSP core is C++ in `sdk/dsp/` (`audioscope::dsp` namespace). The Rust FFI (`rust/src/infrastructure/dsp_ffi.rs`) and the WASM/TS wrapper (`packages/dsp-wasm/`) both call the SAME flat C ABI in `sdk/bindings/ffi/audioscope_ffi.{h,cpp}`. There is no duplicate TS FFT anymore — `packages/dsp-wasm/src/audioscope-dsp.ts` is a thin memory-marshalling wrapper, not a reimplementation.
- **C ABI (the FFI seam):** `audioscope_ffi.h` declares `as_*` C structs + `as_*` free functions. Composite returns (spectrum, harmonics, spectrogram, waveform analysis, compressed waveform) are returned as **malloc'd struct pointers** with inner arrays; callers read fields at fixed offsets then call the matching `as_*_free` (frees inner arrays) + `em_free`/`free` (frees the holder). Array returns (magnitudes, triggered window, generated waveform, resampled) use the **malloc'd pointer + `int* out_len`** pattern — robust across all binding runtimes.
- **WASM build (`sdk/wasm/`):** `emscripten_main.cpp` has `EMSCRIPTEN_KEEPALIVE` `extern "C"` wrappers (`em_*`) over the C ABI. CRITICAL: must be `extern "C"` or symbols get C++-mangled and the JS `EXPORTED_FUNCTIONS` list (by C name) fails to link. `CMakeLists.txt` links the `audioscope_dsp`/`audioscope_common` static libs with `--whole-archive` (KEEPALIVE exports have no C++ callers and would be stripped otherwise). emcc flags: `-O3 -msimd128 -msse -msse2 MODULARIZE=1 EXPORT_ES6=1 EXPORT_NAME=AudioScopeDspModule ALLOW_MEMORY_GROWTH=1`. `build.sh` runs emcmake/emmake and stages `audioscope.{js,wasm}` to `packages/dsp-wasm/dist/`.
- **WASM i64 marshalling gotcha:** Emscripten `ccall`/`cwrap` infers arg types from the C signature; `long long`/`int64_t` args require BigInt at the JS call site (`Cannot convert 0 to a BigInt`). The `em_*` wrappers use **i32** for `holdoff` (samples) and `start_time_ms` (fits in i32: ~24 days) and cast to i64 internally — the underlying `as_*` ABI keeps int64_t. Do not reintroduce `long long` in `em_*` signatures.
- **EXPORTED_FUNCTIONS vs EXPORTED_RUNTIME_METHODS:** `_malloc`/`_free` belong in `EXPORTED_FUNCTIONS` (compiled exports), NOT `EXPORTED_RUNTIME_METHODS` (JS-side helpers like `ccall`/`getValue`/`HEAPF32`). Putting them in the latter causes "undefined exported symbol: _malloc".
- **Vendored LZ4:** `sdk/dsp/third_party/lz4/` (LZ4 1.10.0 sources) makes portable targets self-contained. `compression.cpp` only uses `LZ4_compress_default`, `LZ4_compress`, `LZ4_decompress_safe`. The `audioscope_lz4_vendored` CMake target compiles only `lz4.c`. `AUDIOSCOPE_USE_VENDORED_LZ4=ON` (set in the `wasm` CMake preset) selects it; native builds use system lz4.
- **`packages/dsp-wasm/` package:** `AudioScopeDsp` class is the browser/worklet analog of the Rust `dsp_ffi.rs`. Memory model: alloc f32 into HEAPF32 → call `em_*` → copy result out via `HEAPF32.slice` → free. Struct field offsets are hardcoded constants (wasm32, natural alignment) in `audioscope-dsp.ts` matching `audioscope_ffi.h`. Two scratch pointers (`tmpLenPtr`, `tmpMagPtr`) are reused across calls to avoid per-call malloc churn. The generated `audioscope.js`/`.wasm` are gitignored (regenerated by `build:wasm`); the hand-written `dist/audioscope.d.ts` is force-added so typecheck works in a fresh checkout.
- **Build config:** root `package.json` has `build:wasm` (= `bash sdk/wasm/build.sh`), `build:sdk`, `test:sdk` (ctest), `test:wasm` (vitest). `build` depends on `build:wasm`. `turbo.json` declares `build:wasm`/`build:sdk`/`test:sdk`/`test` tasks (the vitest `test` task depends on `build:wasm`). The stale `dev:web`/`dev:mobile` scripts were removed.
- **Testing parity across all three bindings:** native C++ SDK tests (ctest, 36 tests in `sdk/`), WASM vitest (`packages/dsp-wasm/test/dsp-wasm.test.ts`, 12 tests — loads WASM in Node, FFT on a 440 Hz sine, asserts peak; covers measurements, harmonics, LZ4 round-trip, trigger, generators), and Rust FFI tests (`cargo test`, 31 tests in `rust/`). All three exercise the same C++ core, so parity is provable.

## Web app wiring: dsp-wasm + WebGL2 renderer (architecture migration, Steps 4–5 complete)
- **Single DSP source of truth in the browser:** the web app no longer has a duplicate TS FFT. `apps/vyzorWeb/src/lib/scope-dsp.ts` (radix-2 FFT, `computeSpectrum`, `toDecibels`, `triggeredWindow`, `findTriggerIndex`, `resampleTo`) is **deleted**. All DSP flows through `@audio-scope-view/dsp-wasm` (the C++ core compiled to WASM). The web app's `AudioScopeDsp` calls are the browser/worklet analog of the Rust `dsp_ffi.rs` — same C ABI, same core.
- **Singleton loader (`apps/vyzorWeb/src/lib/dsp-loader.ts`):** `ensureDsp()` (async, kicks off + awaits the WASM load, memoized, failure-tolerant → returns null) and `getDsp()` (sync, returns the loaded instance or null). Shared by `scope-canvas.tsx`, `use-audio-analyzer.ts`, `use-waveform-generator.ts`, `measurements-dialog.tsx`. The WASM module is expensive to instantiate (fetch + compile); it must load exactly once. Hot-path callers (rAF draw loop, capture tick) read `getDsp()` and degrade gracefully (free-run / inline fallback) until loaded — the UI never blocks on module load.
- **Consumers wired:** (1) `scope-canvas.tsx` — spectrum is drawn from a precomputed WASM `Spectrum` (dB magnitudes + frequencies, no `toDecibels` step); `triggeredWindow` calls `dsp.triggeredWindow` (returns `Float32Array | null`); `ensureDsp()` on mount. (2) `use-audio-analyzer.ts` — RMS/peak/frequency via `dsp.computeRms`/`findPeakAmplitude`/`estimateDominantFrequency` (with tiny inline TS fallbacks pre-load). (3) `measurements-dialog.tsx` — Vpp/RMS/DC-offset/frequency via the WASM core. (4) `use-waveform-generator.ts` — the old TS `generateSample` synthesizer in `use-mock-audio-analyzer.ts` is replaced by `dsp.generateWaveform` (C++ sine/square/saw/triangle/noise generators); the generator hook drives the new `WaveformGeneratorDialog` (Activity icon in the top bar), which replaced the non-functioning "test mode".
- **WASM asset serving:** `vite.config.ts` adds `optimizeDeps.include: ["@audio-scope-view/dsp-wasm"]` and `assetsInclude: ["**/*.wasm"]`; the production build emits `dist/client/assets/audioscope-*.wasm` (42K) as a referenced asset. `scripts/static-server.cjs` adds `.wasm → application/wasm` to its MIME map (otherwise the browser refuses to compile/stream the module).
- **Type compatibility:** the ui-store's `triggerEdge: "rising" | "falling" | "auto"` is structurally identical to the WASM `TriggerEdge`, so no adapter is needed. `frame` in `scope-canvas.tsx` is `ArrayLike<number>` (the WASM `triggeredWindow` returns `Float32Array`; held frames are `number[]`), so the `for...of` loop was converted to an index loop (`ArrayLike` is not `Iterable` in strict TS).
- **Root `test:sdk` script bug (fixed):** the script did `cd sdk/build/linux && ctest --preset linux`, but `CTestPresets.json` lives in `sdk/`, so ctest could not find the presets from the build subdir. Fixed to `(cd sdk && ctest --preset linux)`.
- **WebGL2 renderer (`src/lib/webgl/`, Step 5 / spec §C.1 — DONE):** the Canvas2D path in `scope-canvas.tsx` is **fully removed** (no `getContext("2d")` remains). Raw WebGL2 is used directly — **no `regl`/`gl-matrix` deps were added** (the spec offered "regl or raw WebGL2 — decide"; raw was chosen, with a hand-rolled `mat4.ts` for ortho/identity). Renderers (all under `src/lib/webgl/`, barrel `index.ts`): `ScopeRenderer` (instanced line trace), `SpectrumRenderer` (spectrum bars), `SpectrogramRenderer` (2D waterfall texture), plus two the spec didn't enumerate — `GlyphRenderer` (SDF text for labels/readouts) and `OverlayRenderer` (grid/cursors/markers). Shaders: `shaders/{line,spectrum,spectrogram,glyph}.{vert,frag}` + `shaders/index.ts`. `GLContext.from(canvas)` acquires one WebGL2 context per canvas and owns the program cache; `scope-canvas.tsx` instantiates a `RendererBundle` of all five renderers sharing it. View selection: `ui-store.ts` `ScopeView = "time" | "spectrum" | "spectrogram"` (spectrogram is new in this step).
- **WebGL2 fallback decision (spec hazard #11 — resolved as: no Canvas2D fallback):** `GLContext.from()` returns `null` when WebGL2 is unavailable; `scope-canvas.tsx` then `console.warn`s and renders an empty surface (no Canvas2D fallback path). WebGL2 is a hard runtime requirement (Chrome/Edge/Firefox/Safari post-2020 all provide it). Do not reintroduce a Canvas2D path.
- **Waveform Generator (replaces "test mode"):** `test-mode-icon.tsx` + the old test-mode UI are deleted; `WaveformGeneratorDialog` (`components/scope/waveform-generator-dialog.tsx`) + `useWaveformGenerator` (`hooks/use-waveform-generator.ts`) feed the scope from the C++ DSP core via WASM (`dsp.generateWaveform`), so rendering/measurements can be verified without a live audio input. Open the dialog (Activity icon), pick Sine/Square/Sawtooth/Triangle/Noise (+ noise color), and the measurement panel shows expected Vpp/Freq/Win.
- **§C.3 playback worklet repointed to the C++ core (DONE):** `apps/vyzorWeb/src/audio/worklets/audio-streaming-processor.js` no longer just plays PCM chunks — it loads the same WASM `AudioScopeDsp` the live-capture path uses and runs per-block DSP (`_em_compute_magnitudes` + `_em_analyze_waveform`) on the played samples, posting `{type:"frame", magnitudes, analysis, sampleRate}` to the main thread for the WebGL renderer. This unifies the DSP source of truth across live capture and playback. The worklet loads the WASM module by **URL** (the main thread resolves the Vite-hashed `audioscope.js`/`.wasm` URLs via `?url` imports in `use-streaming-playback.ts` and passes them in the `config` message); the worklet can't use a bundler `import` (AudioWorklet global scope, flat public URL). `locateFile` is overridden to point at the binary URL (the default `import.meta.url`-based lookup would resolve relative to the worklet — wrong). DSP load is failure-tolerant: if the module fails to load, audio still plays — only the per-block frames stop (mirrors `dsp-loader`'s degradation). `use-streaming-playback.ts` gained an `onDspFrame` option; the `frame`/`dsp_ready`/`dsp_error` messages are typed in the worklet `.d.ts`. The renderer consumes playback frames with the same shape as live frames.
- **`sdk/common/` completion (spec §A.2 — DONE):** the "future/to be done" comments are gone. `buffer.hpp` now has `PoolAllocator<T>` — a free-list object pool with **stable-address** backing storage (`std::vector<std::unique_ptr<T>>`, so `emplace_back` never invalidates an outstanding pointer) and a lock-free Treiber-stack free list; once warm, `acquire`/`release` touch no heap. `config.hpp`/`config.cpp` now have `from_json`/`to_json` (a tiny dependency-free hand-rolled JSON object parser — `common` stays Layer-1-clean, no nlohmann) + `DspConfig::normalized()` (clamps overlap to [0,1), rounds `fft_size` to next pow2, bounds the spectrogram band to Nyquist, swaps inverted bands) + `parse_window_type`/`window_type_name`. `types.hpp`/new `types.cpp` add `sample_format_size()` + `convert_samples_to_f32()` (S16/S32/F32 → normalized F32, the single normalization path every platform binding calls). **Bug fix while here:** the pre-existing `AudioRingBuffer` had a latent correctness bug — `(w - r) % capacity_` made a full ring indistinguishable from an empty one (so `push` overwrote past capacity and `available()` returned 0 when full). Fixed to use `w - r` (monotonic indices, never wrapped) as the count directly; the modulo is only for the physical slot index. New `sdk/tests/test_common.cpp` (25 tests: ring buffer round-trip/wrap/concurrency, pool reuse/growth/stable-address, JSON parse/round-trip/unknown-keys/malformed, normalization clamps, S16/S32/F32 conversion).
